# 长篇小说阅读导航

把用户提供的长篇小说变成可靠的阅读伴侣：读者应在掌握完整故事的前提下，把注意力集中在最值得完整阅读的章节与段落上。保留原文、区分“重要性”和“内容类型”，并让每个结论都能追溯到章节及原文位置。

## 范围与安全边界

- 将用户提供的小说视为只读源文件。所有衍生文件须与原文分开保存，并记录源文件哈希值、编码和行号/偏移量映射。
- 静态网站默认只在本地交付；除非用户明确授权，不上传、发布或再分发原文。
- 不得仅根据章节标题猜测剧情。未读到的批次必须标为“暂定”，不得编造章节标注。

## 自动化边界

`scripts/` 只能包含确定性、可复用的工具：章节索引、格式转换、数据校验、从已知行号提取原文，以及从规范数据构建网站。脚本必须通过命令行参数或项目元信息接收输入，不能硬编码某部小说、章节范围、人物、篇章或输出目录。

不得创建根据章节标题、关键词、固定章节号、首尾段落拼接或手写剧情列表来生成摘要、阅读优先级、内容标签、人物、关系或篇章的数据脚本。AI 的真实阅读结论应直接写入批次数据文件；若只是在测试索引器或建站器，应使用临时目录中的小型样例数据，绝不能向正式项目写入伪分析结果。

## 工作流

### 1. 准备源文件与章节索引

先创建[数据契约](references/data-contract.md)中的 `guide-project.json`，并以它保存本小说的标题、源文件、处理范围、分析状态、标签体系和网站偏好。识别编码、解析章节标题，并建立“章节 → 原文位置”的导航索引。对于标题形如“第12章 标题”的中文 TXT，直接使用内置的 `scripts/index_novel.py`；它只读源文件并导出 CSV、JSONL 和源文件校验信息。其他标题格式应先调整脚本的 `CHAPTER_RE`，再开始 AI 分析。索引至少保存章节号、标题、起止行号（或字节偏移）、长度、源文件路径、源文件哈希值与解析规则。

TXT 默认输出行号导航，因为它可以直接在常见文本编辑器中定位。其他格式则提供读者可稳定使用的位置标识。保留原始章节编号；不要因为缺章、番外或卷首而自行重排。

### 2. 建立全书暂定骨架

在逐章精读前，对全书进行一次粗扫。利用章节标题、章节边界、抽样或分批阅读，识别主要篇章、显著转折、核心人物和重要关系。

这份骨架只是工作假设，不是最终结论；必须允许后续精读纠正它。不能用一次塞入全文的大摘要代替此步骤。

先输出 `guide-project.json.story` 的暂定版；它必须标明覆盖范围与不确定处。完成所有批次并整合后，再以整合的章节记录重写该字段为最终版。应产出：

- 简短的全书前提、主线和结局概述，并标明剧透等级；
- 按顺序排列的故事篇章、章节范围和关键转折；
- 每位核心人物一句话：角色定位、核心欲望或冲突，以及已知的当前/最终状态；
- 重要人物关系边：双方、关系类型、变化或张力、支撑该判断的章节范围。

### 3. 分批标注章节

默认每批负责约 100 个章节；如故事篇章边界更适合作为切分点，可以调整批次大小。当用户已同意使用委派且子 agent 可用时，优先让子 agent 独立阅读批次；同时保留一名协调者维护唯一的故事总模型。

每批有两个范围：

- `owned_range`：该工作者需输出最终记录的章节；
- `read_range`：`owned_range` 前后通常各扩展两章，用来获得上下文。若大战、调查、试炼或揭密跨越边界，应扩展至该事件的自然起止处。

重叠章节只用于理解上下文，不得为非 `owned_range` 章节输出竞争性的最终记录。给每个工作者提供当前骨架、人物/关系表、必要的前序章节记录，以及明确的两种范围。协调者处理冲突，再更新总模型，供后续有依赖的批次使用。

每个负责章节均须按[数据契约](references/data-contract.md)输出结构化记录，尤其要分清三种维度：

- **阅读优先级**（`intensive`、`must_read`、`quick_read`）回答“应读得多细”；
- **内容标签**（如对话、打斗、言情、悬疑、修炼、喜剧）回答“本章有什么”，可多选；
- **叙事作用**（如铺垫、回收、转折、人物变化）回答“本章推动了什么”，可多选。

`quick_read` 不等于“可安全丢弃”：必须写出读者至少要保留的事实或段落。`intensive` 用于高回报的文字、关键情绪场景、因果复杂的转折，或完整质感很重要的动作戏；`must_read` 用于必要但可以读快一些的因果连接。

批次分析结果按数据契约写入 `data/batches/batch-*.json`，由 `scripts/merge_batches.py` 在核查后合并为 `data/chapters.json`。合并器只验证和汇总，绝不创造内容。协调者随后写入 `arcs.json`、`characters.json`、`relationships.json` 与 `guide-project.json.story`。没有完成真实批次阅读时，项目状态应为 `not_started`，且不得生成可供读者浏览的章节分析数据或网站。

### 4. 整合与质量检查

批次完成后，统一校正篇章边界、同名或别名人物、相互矛盾的摘要、人物关系变化以及伏笔/回收链接。最终应基于整合后的章节记录重写全书骨架，不能把“暂定版”直接当交付物。

检查：

- 每个已索引章节恰好对应一条最终章节记录；
- 每个原文位置均在范围内，索引没有意外重叠；
- 每项重要剧情判断、关系变化和伏笔回收都有支撑章节 ID；
- 每个 `quick_read` 章节都说明了必须记住什么；
- 批次边界前后的记录彼此一致，尤其检查重叠章节附近；
- 标签和优先级足够一致，能够跨全书筛选。

至少抽查每个批次边界附近的一章，以及每个大篇章的一章高优先级章节，回到原文核对。

### 5. 交付本地静态阅读网站

网站应数据驱动，并尽量免构建。采用**确定性的建站工具**：AI 只负责按数据契约产出或修正小说数据，`scripts/build_reading_site.py` 读取经校验的数据和 `guide-project.json`，生成统一的静态站。不要每处理一本小说就让 AI 从零手写页面；仅当需要改变通用界面能力或模板时才修改建站器。不要在首屏加载整本小说：索引和摘要数据保持轻量，只有读者请求“阅读全文”时才加载本章原文。

最低可用网站包括：

- **总览页：** 前提、剧透提示、按顺序的篇章和重大转折；
- **章节浏览页：** 按阅读优先级、内容标签、叙事作用、人物和篇章筛选；展示标题、一句话阅读理由、原文行号和短摘要；
- **章节详情页：** 可展开摘要、关键变化、承接事实、阅读理由、相邻章节与按需加载的全文；
- **人物与关系页：** 一句话人物卡，以及易读的关系列表或关系图。

数据布局和界面要求见[数据契约](references/data-contract.md)。说明如何在本地打开网站（通常是启动一个小型静态服务器）；如果实现依赖 `fetch`，不得声称双击 `file://` 就能正常运行。

建站器的输入是规范数据目录，输出是独立的 `site/` 目录；它可以复制原文分章数据和模板、生成轻量索引、校验链接，但不得自行改写 AI 给出的摘要、标签或人物关系。将建站器作为本 Skill 的版本化脚本维护，供每部小说重复使用。不要使用或扩展任何“根据标题自动生成摘要/优先级”的脚本。

## 交付原则

- 在有帮助时采用渐进剧透：读者可先看到推荐和无剧透引导，再自行展开完整摘要。
- 用简洁、可核对的转述代替大段复制原文。
- 若某一篇章真正可跳内容很少，应明确告诉读者；筛选应保守，目标是节省时间而不是悄悄切断因果或删掉爽点。
- 尽量让机器可读数据成为事实来源，再从中派生 Markdown 或网站页面。
